# Artifact selection

The instinct to produce every artifact in the catalogue is the most common way architecture
documentation fails. Each artifact carries an ongoing cost — someone has to update it, and
someone has to notice when it is wrong. An artifact nobody maintains is worse than no
artifact, because people trust it right up until it burns them.

So the rule is: **an artifact earns its place by answering a question someone is actually
going to ask, or by retiring a risk somebody has named.** If neither applies, do not produce
it, and say why you did not.

## The default floor

Almost any project of any size warrants:

- **Architecture document** with a context view and a container view — what this is, who
  uses it, what the pieces are.
- **ADRs** for the three to six significant decisions.
- **Risk and assumption registers** — usually sections inside the architecture document
  rather than separate files.
- **Artifact index** (`assets/artifact-index-template.md`) once there is more than one
  artifact, so that ownership and review dates live in one findable place.

Everything below is added on a trigger.

## Trigger table

| Produce this | When this is true | Skip when |
|---|---|---|
| Component view | One container has enough internal structure to argue about | Containers are small or conventional |
| Sequence diagrams | A flow crosses a trust boundary, handles money, or has a failure path to design | CRUD over one datastore |
| State machine | A story says "cannot X once Y" or an entity has a lifecycle | Status is a display field with no rules |
| Data model (ERD) | Anything is persisted with relationships that matter | Single flat store, or storage is a vendor's problem |
| Data-flow diagram | Personal or regulated data moves between components or jurisdictions | No sensitive data crosses a boundary |
| Trust boundary diagram | External exposure, multi-tenancy, or regulated data | Single-tenant internal tool with SSO |
| Threat model | Domain 4 in play — personal, regulated, financial data, or internet exposure | Internal tool, no sensitive data, no external surface |
| Deployment / network diagram | Non-trivial topology, network controls, or self-updating software | Single managed platform with defaults |
| Capacity plan / performance budget | A stated latency or throughput NFR, or usage-based cost risk | Load is trivially within one instance |
| Failure-mode analysis | Failure has financial, safety, or contractual consequence | Failure means a user retries |
| Test strategy | More than one person or team verifies the system, or there are compliance test obligations | One developer, one test suite, low stakes |
| Integration / dependency inventory | Three or more external dependencies, or any critical vendor | One well-known dependency |
| API or event catalogue | Interfaces are consumed by teams or systems outside this one | Internal-only interfaces changed by the same team |
| Migration / transition plan | Something is being replaced, or a decision is transitional | Greenfield with no legacy and no transitional choices |
| Current-state architecture | A system exists and is being changed or replaced | True greenfield |
| Ownership matrix / RACI | More than one team, or unclear operational ownership | One team owns everything |
| Cost model | Budget ceiling, usage-based pricing, or a lock-in question | Fixed, small, predictable hosting cost |
| Observability / SLO definition | Runs unattended, or anyone is on call | Desktop tool, or a human notices immediately |
| Technical-debt register | Known compromises are being accepted deliberately | No knowing compromises yet |
| Compliance mapping | A named regime applies and someone will audit it | No regulatory exposure |

## Selection heuristics

**Ask what decision the artifact supports.** A diagram that nobody would consult before
making a change is decoration. If you cannot name the decision or the review it feeds, cut it.

**Prefer sections to files.** A risk register inside the architecture document is more likely
to stay current than a separate `risks.md` nobody opens. Split it out when it grows past
about a page or gains its own audience.

**Match the artifact to the audience that will read it.** A threat model is read by security
reviewers, a runbook by whoever is on call, an ADR by the engineer who wants to change the
decision in a year. An artifact with no identified reader is being written for the archive.

**Prefer generated to hand-maintained.** The traceability matrix is generated by
`scripts/check_coverage.py`; diagram images are generated from the Mermaid source. Anything
maintained in two places will disagree in two places.

**Fewer, richer artifacts beat many thin ones.** Five thorough documents get maintained;
twenty stubs do not, and the stubs make the record look more complete than it is.

## Presenting the selection

Give the user the list with a one-line justification tied to a driver or risk, plus what you
deliberately excluded. Then let them cut it — they know their organisation's appetite better
than you do.

> Given the personal data and the external exposure, I'd produce: architecture document
> (context + container + two sequences), four ADRs, a data-flow diagram, and a threat model.
> I'd skip the capacity plan — 40 internal users is nowhere near needing one — and the RACI,
> since one team owns everything. Say if you want either back.

Record the exclusions in the artifact index. An unexamined domain and a deliberately
excluded one look identical in the final documentation unless the exclusion is written down,
and a reviewer who cannot tell them apart has to re-open all of them.
